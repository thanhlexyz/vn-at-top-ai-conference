Huynh Quyet Thang (HUST) · All professors

Language models and NLP (1 paper · CSRankings score 0.20)

Topic description

Most evaluations of LLMs for code target imperative languages, so their ability in functional languages is little studied. The paper introduces a benchmark of 721 tasks in Haskell, OCaml and Scala, with executable tests and static analysis, and uses Java as an imperative baseline. It reports higher error rates in Haskell and OCaml, frequent non-idiomatic imperative-style code, and partial self-repair from static-analysis feedback.

Papers (1)
Perish or Flourish? A Holistic Evaluation of Large Language Models for Code Generation in Functional Programming EMNLP 2026 · rejected
The problem
Functional programming supports reliable and secure software but is hard to learn, and LLM code generators could lower that barrier; however, most evaluations of LLMs for code target imperative languages, so their ability in functional languages is little studied.
The idea
The paper introduces FPEval, an evaluation framework with FPBench, a benchmark of 721 tasks at three difficulty levels in Haskell, OCaml and Scala, combining executable test suites for correctness with static-analysis tools for code style and maintainability; Java is included as an imperative baseline.
Strengths
Evaluating seven LLMs including GPT-5 and Claude Opus 4.6, the paper reports that error rates are higher in Haskell and OCaml than in Scala or Java, that models often produce non-idiomatic code following imperative patterns, and that static-analysis feedback lets models partially repair both correctness and quality issues.
What the authors leave open
  • The benchmark covers only Haskell, OCaml and Scala, so the authors note the results may not generalize to other functional languages and leave broader language coverage to future work.
  • Claude Opus 4.6 is excluded from the self-repair evaluation because the multi-turn repair loop is costly in API usage; extending this evaluation is left to future work.

Knowledge representation and reasoning (1 paper · CSRankings score 0.12)

Topic description

More than half of vulnerability database entries have missing or incorrect information about which library is affected. The paper builds a security knowledge graph linking vulnerability entries, libraries, weakness types, product identifiers and software ecosystems, predicts missing vulnerability-library links, and re-ranks candidates with a fine-tuned LLM. Papers (1)
Athena: Vulnerability-Affected Library Identification via Knowledge Graph Completion EMNLP 2026 · accepted
The problem
A vulnerability in a widely used library can propagate to many dependent applications, yet the paper reports that more than half of vulnerability database entries have missing or incorrect information about which library is affected. Existing automated methods treat this identification as isolated text retrieval and ignore the relational structure of the databases.
The idea
Athena builds a security knowledge graph linking CVEs (Common Vulnerabilities and Exposures entries), libraries, CWE weakness types, CPE product identifiers and software ecosystems, and casts identification as knowledge graph completion, i.e. predicting missing CVE-library links. Candidates from the link-prediction backbone are then re-ranked by a fine-tuned LLM that also receives knowledge graph embeddings.
Strengths
On the VulLib dataset the paper reports a 32% improvement in average F1 over the best baseline (VulLibGen), and its 110M-parameter graph-completion backbone alone already surpasses VulLibGen's best 7B configuration.
What the authors leave open
  • The authors' error analysis attributes most failures to newly introduced libraries with little historical evidence in the graph and to confusion among closely related libraries, such as Jenkins workflow plugins mistaken for other pipeline plugins.
  • Some failures come from cross-ecosystem redistribution: an advisory names an upstream product (for example Google Chrome) while the affected package (electron) is distributed in another ecosystem, and no graph edge connects the two.
  • The authors leave further improvement of the LLM re-ranking stage to future work.
